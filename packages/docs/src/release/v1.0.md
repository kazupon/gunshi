# Gunshi v1.0 Release Notes

Gunshi v1.0 is the first stable release of Gunshi.

This page describes what changed since v0.37.3. To learn what Gunshi is and how to use it, start with the guide: [What's Gunshi?](../guide/introduction/what-is-gunshi.md), [Getting Started](../guide/essentials/getting-started.md), [Plugin System](../guide/essentials/plugin-system.md), and the [API References](/api/).

If you are upgrading from v0.37.3, read the 💥 Breaking Changes section. It ends with a [migration checklist](#migration-checklist). The [CHANGELOG](https://github.com/kazupon/gunshi/blob/main/CHANGELOG.md) lists every change.

## 🌟 Features

### Parser Combinators Are Stable

The parser combinators of `gunshi/combinators` and `@gunshi/combinators` are no longer experimental. They build an argument schema from composable factories, with types inferred from the factories:

```ts
import { define } from 'gunshi'
import { string, integer, boolean, withDefault, short } from 'gunshi/combinators'

const command = define({
  name: 'serve',
  args: {
    host: withDefault(short(string({ description: 'Host to bind' }), 'h'), 'localhost'),
    port: withDefault(
      short(
        integer({
          min: 1,
          max: 65535,
          description: 'Port number'
        }),
        'p'
      ),
      8080
    ),
    verbose: short(boolean({ description: 'Enable verbose output' }), 'v')
  },
  run: ctx => {
    // ctx.values.host is typed as string, and ctx.values.port as number
  }
})
```

The guide moved from Experimentals to [Advanced: Parser Combinators](../guide/advanced/parser-combinators.md). The old URL redirects to it.

The value types of the combinators are more precise in v1.0, which can surface type errors in existing code. See [args-tokens 1.0](#args-tokens-1-0).

### Option-Aware Command Routing

Gunshi now reads the values of options before it chooses a sub-command, so an option that takes a value can be written before the command name:

```sh
# `config` is a global string option, added by a plugin
my-cli --config prod.json deploy              # runs `deploy` with config 'prod.json'
my-cli remote --config prod.json add origin   # runs `remote add`
my-cli --config clean deploy                  # runs `deploy`: `clean` is the value of `--config`
```

v0.37.3 chose the command from the first positional argument without looking at the options, and reported `Command not found: prod.json` for the first line.

When the options do not identify one command, Gunshi runs no command and reports a `CommandResolutionError` inside the `AggregateError` of the validation errors, which `onErrorCommand` receives:

```js
import { cli, isCommandResolutionError } from 'gunshi'

await cli(process.argv.slice(2), entry, {
  subCommands,
  onErrorCommand: (_ctx, error) => {
    if (error instanceof AggregateError) {
      const resolutionError = error.errors.find(isCommandResolutionError)
      if (resolutionError) {
        console.error(resolutionError.code) // e.g. 'err:cmd:inconsistent-options'
        console.error(resolutionError.candidatePaths) // e.g. [['clean'], ['deploy']]
      }
    }
  }
})
```

The error has one of three codes, `err:cmd:ambiguous`, `err:cmd:inconsistent-options` and `err:cmd:lazy-schema-mismatch`, and its message is localized with the i18n plugin like the other errors. Some inputs that worked in v0.37.3 now behave differently. See [Command Routing](#command-routing).

### Commands Own the Names They Declare

`help`, `version` and the names that plugins add as global options are not reserved. A command may declare an argument under such a name, and the command now owns it:

```js
import { define } from 'gunshi'

const release = define({
  name: 'release',
  args: {
    version: { type: 'string', description: 'Version to release' }
  },
  run: ctx => console.log(`releasing ${ctx.values.version}`)
})
```

`my-cli release --version 1.2.3` runs the command with `1.2.3`. v0.37.3 printed the version of the CLI instead. This holds whatever the schema is, even one identical to the schema of `@gunshi/plugin-global`.

- **Short names work the same way.** A command that declares `verbose: { type: 'boolean', short: 'v' }` takes `-v`. The global `--version` keeps its long name, and the help of that command lists it as `--version` alone
- **Between global options, the first one keeps the short name.** When two plugins add global options with the same short name, the one registered first keeps it, and the other is registered without it, with a warning
- **Plugins can tell whether their global options are in effect.** `ctx.env.globalOptions` holds the global options that are in effect for the running command. `@gunshi/plugin-dryrun` uses it to stay off, with a warning, for a command that declares an argument named after its option

```ts
import { plugin } from 'gunshi/plugin'

export default plugin({
  id: 'debug',
  setup: ctx => {
    ctx.addGlobalOption('debug', { type: 'boolean', description: 'Enable debug output' })
  },
  extension: ctx => {
    // `undefined` when the context was built on its own, as in a plugin's own unit tests
    const inEffect = ctx.env.globalOptions?.has('debug') ?? true
    const debug = inEffect && ctx.values.debug === true
    return {
      log: (message: string) => {
        if (debug) {
          console.log(`[debug] ${message}`)
        }
      }
    }
  }
})
```

See [Plugin Extensions](../guide/plugin/extensions.md) for the pattern.

### Shell Completion That Follows the CLI

`@gunshi/plugin-completion` now completes what the CLI accepts:

- The global options, such as `--help` and `--version`
- The entry command of a CLI without sub-commands
- Option names converted by `toKebab`, such as `--dry-run`
- What follows a boolean option, where the completion used to stop
- The `--no-<name>` form of a negatable option, described as in the help, also with the i18n plugin
- The arguments that the loader of a lazy command defines
- The value of an option after its short name, when a global option uses the same short name

It no longer completes `hidden` arguments, and the "Did you mean" hint of `@gunshi/plugin-suggestion` no longer suggests them. They are still accepted.

### Report Expected Failures With `CommandError`

A command reports a failure that it expects, such as a project that does not exist, by throwing a `CommandError`. Gunshi prints its message to stderr, without a stack trace, with a `Caused by:` line for each cause, and sets the exit code to the `exitCode` of the error, `1` by default:

```ts
import { CommandError, define } from 'gunshi'

export default define({
  name: 'show',
  args: { project: { type: 'positional' } },
  run: async ctx => {
    const project = await findProject(ctx.values.project)
    if (!project) {
      throw new CommandError(`Project ${ctx.values.project} not found`, {
        code: 'not_found',
        exitCode: 2
      })
    }
    ctx.log(project.description)
  }
})
```

```sh
$ my-cli show acme
Project acme not found
$ echo $?
2
```

The `cli()` promise resolves, as it does for the argument errors, and `onErrorCommand` is called with the error after the exit code is set. Any other error thrown by a command rejects `cli()` as before. See [Errors and Exit Codes](../guide/essentials/errors.md).

The loader of a lazy command can throw a `CommandError` too, for a failure while loading, such as a package that is not installed: Gunshi reports it where the command runs.

### Output JSON With `--json`

`--json` is designed for AI agents first. An agent that runs your CLI reads the result as data, not as text for people, and when the command fails, the error tells the agent why and, when the input can be fixed, which command to run next, so the agent can correct the command by itself.

A command supports `--json` when it spreads `jsonArgs` into its arguments. It returns its result from `run`, as an object keyed by a noun, and prints the lines for people with `ctx.log`. With `--json`, Gunshi prints the result as one JSON document to stdout, and a failure as one line of JSON to stderr:

```ts
import { define, jsonArgs } from 'gunshi'

export default define({
  name: 'list',
  args: { ...jsonArgs },
  run: async ctx => {
    const projects = await fetchProjects()
    for (const project of projects) {
      ctx.log(project.name)
    }
    return { projects }
  }
})
```

```sh
$ my-cli list --json | cat
{"projects":[{"name":"acme-web"},{"name":"acme-api"}]}
$ my-cli show nope --json
{"status":"error","reason":"not_found","message":"Project nope not found"}
```

The errors have `status`, `reason`, `message`, `next` (the help of the nearest command, when its `--help` shows the help) and `data`, after the CLI guidelines of Vercel, and the `code` of a `CommandError` is the `reason`. The types check what `run` returns: an object for a command that spreads `jsonArgs`, and a string or nothing for any other command. See [JSON Output](../guide/essentials/json-output.md).

## ⚡ Improvement Features

### Clearer Argument Errors

Gunshi v1.0 is built on args-tokens 1.0, which reports more cases with an error code of their own:

| Code                       | Reported when                                                                                           |
| -------------------------- | ------------------------------------------------------------------------------------------------------- |
| `err:arg:missing-value`    | An option that takes a value has none (`--port`), or the next argument starts with a dash (`--port -5`) |
| `err:arg:unexpected-value` | The negated form of a boolean option is given a value (`--no-color=false`)                              |
| `err:arg:conflict`         | Arguments declared with `conflicts` are used together                                                   |
| `err:arg:invalid-default`  | The default of an `enum` argument is not one of its `choices`                                           |

A value that starts with a dash gets a hint:

```txt
Option '--port' or '-p' requires a value (to pass '-5' as its value, write '--port=-5')
```

With the i18n plugin, the hint follows the translated error, and is translated with the new built-in key `err:arg:missing-value:hint`. The built-in translation of `err:arg:required-positional` now names the argument by its display name, as the other translations do, such as `Positional argument 'input-file' is required` with `toKebab`.

### Argument Errors Point to the Help

An argument error is followed by the command that shows the help of the nearest command: the command itself for a wrong argument, and the parent for an unknown command, whose message is the same at every level.

```sh
$ my-cli records nope
Command not found: nope

See the arguments of the command:
  my-cli records --help
```

It is the command that `next` of the JSON error has with `--json`, and it follows the hints of the suggestion plugin and the message of your own `renderValidationErrors`. Without the `name` of `cli()`, the command starts with `<COMMAND>`, and the heading says to replace it. To leave it out, pass `helpHint: false` to `cli()`. See [Errors and Exit Codes](../guide/essentials/errors.md#argument-errors).

### Help Output That Describes Each Command

The usage that `--help` and `generate()` render is more accurate:

- Each row of the COMMANDS section shows the arguments of its own command, not those of the running command

  ```txt
  COMMANDS:
    [greet] [OPTIONS] <name>          Greet someone
    push <remote>                     Push things
    status                            Show status
    tidy [OPTIONS]                    Tidy up
  ```

  v0.37.3 showed `<OPTIONS> <name>`, the symbols of the running command, on every row

- The USAGE line shows `[OPTIONS]` for the options that may be left out, and spells out each required option, such as `deploy [OPTIONS] --name <name>`. The rows of the COMMANDS section show the required options of their commands in the same way. v0.37.3 showed `<OPTIONS>` whenever an option had no default, which `--help` and `--version` made true for every command
- The value of an option is in angle brackets whether the option has a default or not, such as `--count <count>  How many instances (default: 1)`, since the value cannot be left out. v0.37.3 showed `[count]` for an option with a default other than `0`, `''` and `false`
- The negated form of a negatable option is described as `Negate --verbose`, and `--verbose を打ち消す` in Japanese, in the help and in the shell completion. v0.37.3 described it as `Negatable of --verbose`
- The "For more info" block of a CLI without a `name` shows `COMMAND --help`, not `undefined --help`
- With the i18n plugin, the COMMANDS section shows the localized description of each command
- The columns are aligned by the width that a terminal draws, so full-width characters, combining characters and emoji no longer shift them
- The top-level COMMANDS section lists the entry command when plugins add the other commands
- The USAGE line of a sub-command that has sub-commands shows its path, such as `git remote [COMMANDS] [OPTIONS]`. v0.37.3 showed the usage line of the CLI, `git [COMMANDS] <OPTIONS>`
- A command without `run` is no longer listed as the default command, such as `[remote]`, in the COMMANDS section and the "For more info" block
- An argument whose name starts with `no-` is described by its own description, and a negated form that renders under the same name as an argument is no longer listed twice. Three cases that made `--help` throw are fixed
- An `enum` argument that has a `parse` function and no `choices` no longer makes `--help` and `generate()` throw
- `generate()` returns the usage of a command that declares an argument named `help` or `version`
- A row of the ARGUMENTS or OPTIONS section without a description, and a blank line of the EXAMPLES section, no longer end with spaces

### Lazy Commands Keep Their Definition

- When the loader returns a command object, the properties of the definition that the command object does not set, such as `args` and `description`, are kept
- The `toKebab` and `rendering` of a lazy command apply
- A lazy entry command without a `name` runs
- `withI18nResource()` of `@gunshi/plugin-i18n` returns a lazy command for a lazy command. v0.37.3 returned an object that did nothing when it ran

### Faster Shell Completion

`@gunshi/plugin-completion` registers the completions only inside its `complete` command, and only for the command path being completed. A CLI with 1,000 sub-commands, the i18n plugin and the completion plugin used to spend about 360 ms on every run to register them. It now spends well under a millisecond.

### Sub-Commands on the Main Command, or in an Array

The `subCommands` of the entry command are now the sub-commands of the CLI when `cli()` gets no `subCommands`, as with any other command definition. `subCommands` can also be an array of commands, which are keyed by their names:

```ts
const main = define({ name: 'todo', subCommands: [add, list] })

await cli(process.argv.slice(2), main)
```

In an array, every command needs a name, and no two commands can have the same name. Otherwise, `cli()` rejects with a `TypeError`.

### Gunshi Ships a Guide for Coding Agents

The `gunshi` package ships a guide for coding agents, `AGENTS.md`, for the installed version: a complete example, the rules that the example does not show, and which guide to read for a task. Its rules include how to report the failures that a command expects with `CommandError`, and how to support `--json` with `jsonArgs`. Point your AI agent at it from `AGENTS.md` or `CLAUDE.md`, as the [manual setup](../guide/introduction/setup.md#manual-setup) shows.

`gunshi` also ships an [agent skill](https://docs.anthropic.com/en/docs/claude-code/skills) at `skills/gunshi/SKILL.md`. Package managers that link the agent skills of dependencies, such as pnpm v12, make it available to your AI agent once its skills are approved. The skill has the agent read the guide, and add the instructions to `AGENTS.md` or `CLAUDE.md`. To let the agent read the guides and the API references in Markdown, install `@gunshi/docs` at the same version as `gunshi`.

## 💥 Breaking Changes

### Upgrade Gunshi and the Official Plugins Together

Upgrade `gunshi` (or `@gunshi/bone`) and the official plugins to v1.0 together. The plugins rely on what the v1.0 core provides. For example, `@gunshi/plugin-global` v1.0 handles `--help` and `--version` only when `ctx.env.globalOptions` says that they are in effect, and the v0.37.3 core does not provide it: with `@gunshi/bone` v0.37.3, `--help` and `--version` would run the entry command instead. `gunshi` bundles its built-in plugins, so this matters when you install the plugins yourself.

### Deno and JSR Are No Longer Supported

Gunshi v1.0 no longer supports Deno, and is no longer published to JSR. The Deno runtime gets bug fixes and security updates for one more year, after which its development ends ([Deno blog](https://deno.com/blog/cloudflare)). Gunshi v1.0 is tested on Node.js and Bun, and published to npm. The versions already published to JSR stay there.

**How to migrate**

- Run your CLI with Node.js (v22 or later) or Bun (v1.1 or later)
- If you installed Gunshi or its plugins from JSR (`jsr:@gunshi/...`), install them from npm instead (`gunshi`, `@gunshi/...`)

### args-tokens 1.0

Gunshi reads the arguments with args-tokens 1.0, which reads them more strictly and as they are written.

**Options that take a value**

| Input                                                      | v0.37.3                    | v1.0                                 |
| ---------------------------------------------------------- | -------------------------- | ------------------------------------ |
| `--name` (a `string` option, no value)                     | `err:arg:invalid-type`     | `err:arg:missing-value`              |
| `--level` (an `enum` option, no value)                     | `err:arg:invalid-choice`   | `err:arg:missing-value`              |
| `--port` (a `number` option, no value)                     | rejects with a `TypeError` | `err:arg:missing-value`              |
| `--port -5`                                                | rejects with a `TypeError` | `err:arg:missing-value`, with a hint |
| `-p=-5`, `-p-5`                                            | reject with a `TypeError`  | `-5`                                 |
| `-n=-foo`                                                  | `'foo'`                    | `'-foo'`                             |
| `--name=` (with a default)                                 | the default                | `''`                                 |
| A `multiple` option with a default of `'latest'`           | `'latest'`                 | `['latest']`                         |
| An `enum` option whose default is not one of its `choices` | the default                | `err:arg:invalid-default`            |

`--port=-5` and `--port 5000` work as before.

**Boolean options**

| Input                             | v0.37.3                        | v1.0                       |
| --------------------------------- | ------------------------------ | -------------------------- |
| `--verbose=false`                 | `true`                         | `false`                    |
| `--verbose=0`, `--verbose=`       | `true`                         | `err:arg:invalid-type`     |
| `--help=false`, `--version=false` | print the usage or the version | run the command            |
| `--no-color=false`                | `color: false`                 | `err:arg:unexpected-value` |
| `--color=false` (negatable)       | `true`                         | `false`                    |

**Positional arguments and `--`**

| Input                                                                      | v0.37.3                   | v1.0               |
| -------------------------------------------------------------------------- | ------------------------- | ------------------ |
| A `multiple` positional argument with a default of `'index.js'`, not given | no value                  | `['index.js']`     |
| `--verbose -- ''`                                                          | `''` in `ctx.positionals` | `''` in `ctx.rest` |

**Definitions that are now rejected on every run**

| Definition                                            | v0.37.3                                 | v1.0                                                    |
| ----------------------------------------------------- | --------------------------------------- | ------------------------------------------------------- |
| An `enum` argument with neither `choices` nor `parse` | runs, but `--help` throws               | every run rejects with a `TypeError`, `--help` included |
| A `custom` argument without `parse`                   | rejects only when the argument is given | every run rejects with a `TypeError`                    |

**Error codes and types**

- The four new codes are listed in [Clearer Argument Errors](#clearer-argument-errors). A conflict between arguments now has a code, `err:arg:conflict`
- The value types of the parser combinators are more precise. For example, `describe(required(string()))` is `string`, not `string | undefined`, and `positional(multiple(integer()))` is `number[] | undefined`
- The resolver validates more, so the bundled JavaScript is larger: about 96 KB for `@gunshi/bone`, from about 79 KB

**How to migrate**

- Handle `err:arg:missing-value` and the other new codes where you branch on the code or on the English message of a validation error, as in a custom `renderValidationErrors`. If you check that every `ArgsValidationErrorCode` is handled, add the four codes
- If you pass your own translations of the built-in resources, add the new keys. Without them, the English message is shown. If you type them as `Record<BuiltinResourceKeys, string>`, the new keys are required
- Give an `enum` argument its `choices` (or a `parse` function), and a `custom` argument its `parse` function. Choose the default of an `enum` argument from its `choices`
- Write a value that starts with a dash after `=` or right after a short option: `--port=-5`, `-p=-5` or `-p-5`
- Stop giving a value to the negated form of a boolean option. To give a value, use the positive form: `--color=false`
- Read the default of a `multiple` argument as an array, and an empty argument after `--` from `ctx.rest`
- Fix the type errors that the more precise types of the parser combinators surface

### Command Routing

[Option-aware command routing](#option-aware-command-routing) changes which command some inputs select.

**Inputs that now work**

| Input                                                | v0.37.3                                                   | v1.0                               |
| ---------------------------------------------------- | --------------------------------------------------------- | ---------------------------------- |
| `--config prod.json deploy` (a global string option) | `Command not found: prod.json`                            | runs `deploy`                      |
| `--config clean deploy`                              | runs `clean`                                              | runs `deploy`                      |
| `--unknown x deploy`                                 | `Command not found: x`                                    | runs `deploy`                      |
| `'' build x`                                         | gives `build` to the first positional argument of `build` | gives `x` to it, as `build x` does |

**Inputs that now report an error**

| Input                                                                                                             | v0.37.3      | v1.0                           |
| ----------------------------------------------------------------------------------------------------------------- | ------------ | ------------------------------ |
| `--verbose build` (`verbose` is declared only by the entry command)                                               | runs `build` | `err:cmd:inconsistent-options` |
| `--config clean deploy`, when `deploy` declares `config: { type: 'boolean' }`                                     | runs `clean` | `err:cmd:inconsistent-options` |
| `--config clean deploy`, when only the loader of the lazy command `deploy` declares `config: { type: 'boolean' }` | runs `clean` | `err:cmd:lazy-schema-mismatch` |

Some inputs now run the entry command instead of a sub-command. See [Inputs That Now Run the Entry Command](#inputs-that-now-run-the-entry-command).

**How to migrate**

- Write options after the command name. To write an option before it, declare the option as a global option, or as an argument of the sub-command
- For a lazy command, declare the options written before its name in the definition passed to `lazy()`, with their `type`, `short`, `negatable` and `toKebab`. Its loader is not run to choose the command
- Handle `CommandResolutionError` where you handle the errors of `cli()`, and translate the three `err:cmd:` keys if you pass your own translations

### A Plugin That Fails to Install Stops the CLI

When the `setup` of a plugin throws, `cli()` now rejects with an error that names the plugin (``Failed to install the plugin `<id>` ``), with the original error as its `cause`. The plugins after it are not installed, and no command runs. v0.37.3 printed `Error loading plugin: …` and went on with the rest.

A plugin whose `id` is empty is rejected with `Plugin id must be a non-empty string`. v0.37.3 dropped it without a word.

The official plugins do not throw in `setup`. The usual cause is two plugins that add a global option with the same name.

**How to migrate**: fix the cause that the `cause` of the error names. Move the work that may fail out of `setup`, into an extension or a decorator. Give every plugin an `id`.

### The Header Comes With the Usage

The header, such as `my-cli (my-cli v1.0.0)`, is now shown with the usage only: for `--help`, and when a command shows its usage with `showUsage()`. v0.37.3 also showed it before every command ran, so it came before what the command printed, such as JSON, and before the validation errors.

`showUsage()` now returns the header and the usage, and `renderHeader` is called only when the usage is shown. With `renderUsage: null`, `--help` no longer shows the header alone.

**How to migrate**

- To show the header before the output of a command as before, call `showHeader()` of `ctx.extensions['g:global']` in the command
- If `renderHeader` printed something before a command ran, such as a banner, move it into the command, or into the `onBeforeCommand` hook of `cli()`
- To keep the usage without a header, set `renderHeader: null`. Removing your `renderHeader` only would show the default header with `--help`

### A Command With Sub-Commands and No `run` Prints Its Usage

When a command that has sub-commands and no `run` runs without a sub-command, such as `my-cli remote`, or `my-cli` when the entry command has no `run`, it now prints its usage to stdout and resolves `cli()` with it, as `--help` does. The exit code is `0`. v0.37.3 printed only the header.

A command with `run` still runs it, with `ctx.omitted` set to `true`. `@gunshi/bone` still prints nothing.

**How to migrate**

- Remove the `run` that only printed the usage of a command that groups sub-commands
- To do something else, or nothing, when such a command runs without a sub-command, give it a `run`

### A Command Without `run` or Sub-Commands Fails

A command without `run` and without sub-commands now throws `TypeError: 'run' is required in command: <name>` when it runs, and `cli()` rejects with it, as for a lazy command whose loader returns a command without `run`. v0.37.3 printed only the header, and the exit code was `0`. `--help` still prints its usage, and `@gunshi/bone` fails the same way. With `--json`, the failure is `command_failed`.

**How to migrate**

- Give `run` to every command that has no sub-commands
- A command that is listed in the help before it is implemented needs a `run` that says so

### Errors While a Lazy Command Loads Are Reported Where It Runs

An error thrown while a lazy command loads is now thrown where the command runs, after the plugins and `onBeforeCommand`, as an error of `run` is: `onErrorCommand` sees it, and with `--json`, the failure is JSON. v0.37.3 rejected `cli()` with it before the arguments were parsed, and `--help` of the command failed too. Until the command runs, the definition given to `lazy()` stands for it, so `--help` prints its usage.

A loaded command without `run` is a command without `run`: it fails when it runs, and a lazy group prints its usage. `resolveLazyCommand()` of `gunshi/utils` no longer throws for it.

**How to migrate**

- An app that reports the errors of a loader from the rejected `cli()` sees them in `onErrorCommand` first: report them in one of the two
- Throw a `CommandError` from a loader for a failure that people can fix, such as a package that is not installed
- A plugin that calls `resolveLazyCommand()` checks `run` of the command that it returns

### Argument Errors Go to stderr, and `cli()` Does Not Reject

When the arguments are wrong, the message is now printed to stderr, the exit code is set to `1`, and `cli()` resolves with `undefined`. v0.37.3 printed the message to stdout and rejected the promise of `cli()`, so a plain `await cli(...)` ended with a stack trace. `onErrorCommand` is still called with the errors, after the exit code is set.

The errors are followed by [the command that shows the help](#argument-errors-point-to-the-help).

With `renderValidationErrors: null`, a renderer that returns an empty message, or `usageSilent: true`, nothing is printed, and `cli()` rejects with the `AggregateError` as before. An error thrown by a command also rejects as before.

**How to migrate**

- To report the errors yourself, set `renderValidationErrors: null` and catch the `AggregateError`
- To use another exit code, or to look into the errors, use `onErrorCommand`
- If you caught the rejection while Gunshi printed the errors, move that code to `onErrorCommand`: the catch no longer runs
- Capture stderr in the tests and snapshots that captured the error messages on stdout
- If your `renderValidationErrors` points to the help itself, pass `helpHint: false` to `cli()`, so that the help is not pointed to twice

### `--json` Belongs to Gunshi

`--json` given to a command that does not spread `jsonArgs` now stops the command before it runs: Gunshi prints `json_not_supported` as one line of JSON to stderr, and sets the exit code to `1`, with or without `strict`. v0.37.3 ignored it, or reported an unknown option with `strict`. A command that declares a `json` argument of its own is not touched.

With `--json`, the argument errors and an unknown command are printed as one line of JSON instead of text.

The types of the results changed too:

- `onAfterCommand` receives the result only when it is a string. A runner written in JavaScript that returned another value passed it to the hook, against its type
- The runner of a `CommandDecorator` returns `string | void | JsonResult`. A decorator that uses the result as a string has a type error
- What `run` may return depends on the arguments (`CommandRunnerResult`). A collection typed with `Command` without type arguments, such as `Record<string, Command>`, does not take a command that spreads `jsonArgs`

**How to migrate**

- To keep a `--json` of your own, keep declaring a `json` argument without `jsonArgs`
- Type a collection of commands with `SubCommandable`, and one command with `define` or `Command<{ args: typeof args }>`
- In `onAfterCommand`, do not expect a result that is not a string
- In a command decorator, return what the runner returns, as it is

### Command Definitions Reject Unknown Keys

`define`, `defineWithTypes`, `lazy` and `lazyWithTypes`, and `defineI18n`, `defineI18nWithTypes` and `withI18nResource` of `@gunshi/plugin-i18n`, now reject a key that a command does not have, such as `desc` or a misspelled `subcommands`, with a type error at the key. So does `cli()`, for an object given as a command or in the table of the sub-commands, since `SubCommandable` no longer takes any key. v0.37.3 accepted such a key, and the CLI ignored it. Only the types changed: the CLI does the same at run time.

A runner given as a sub-command, such as `subCommands: { add: async () => {} }`, is a type error too: the CLI calls a function there as a loader, which returns the command. So is a loader in an array of sub-commands, which the CLI keys by the names of the commands.

The definition of `lazy` and `lazyWithTypes` rejects `run` too, with a type error at the key: a lazy command takes `run` from its loader. v0.37.3 never used a `run` in the definition: the CLI dropped it when the loader returned a runner, and threw `'run' is required in command` when the loader returned a command without `run`. A `run` that is optional in the type, as in the result of `define()` without `run` or a value of the `Command` type, is fine.

**How to migrate**

- Fix the typos: the CLI ignored those keys anyway
- Remove the keys of your own from your commands and from the values typed as `SubCommandable`: a command takes only the keys that Gunshi defines. Keep such data apart from the command
- Give `resource` with `defineI18n` or `withI18nResource(define(...), resource)`, rather than with `define({ resource })` or on an object in the table of the sub-commands. `lazy(loader, { resource })` is fine
- Wrap a runner given as a sub-command with `lazy()`, or define the command. In an array of sub-commands, give the commands, or key the loaders in an object
- Remove `run` from the definition of `lazy`, and return it from the loader: the CLI did not use it

### `@gunshi/docs` No Longer Has a Setup Command

`@gunshi/docs` no longer has the `gunshi-docs-init` command, so `npx @gunshi/docs` no longer works. In v0.37.3, the command wrote the `use-gunshi-cli` skill to `.claude/skills/`, added a "CLI Development" section to `CLAUDE.md`, and offered to install `gunshi` and `@gunshi/docs`. The [guide and the agent skill that Gunshi ships](#gunshi-ships-a-guide-for-coding-agents) take its place.

**How to migrate**

- With a package manager that links the agent skills of dependencies, such as pnpm v12, let the agent skill of `gunshi` set up your agent instructions
- Otherwise, follow the [manual setup](../guide/introduction/setup.md#manual-setup)
- The skill and the section in `CLAUDE.md` that the command wrote stay in your project. To move to the new setup, replace them with the instructions of the agent skill or the manual setup

### Behavior Changes From Bug Fixes

The following changes fix bugs, but they change what some CLIs do, so they may look like breaking changes when you upgrade.

#### Global Options and the Commands That Declare Their Names

| CLI and input                                                                                    | v0.37.3                                             | v1.0                                                                          |
| ------------------------------------------------------------------------------------------------ | --------------------------------------------------- | ----------------------------------------------------------------------------- |
| `release --version 1.2.3`, `release` declares `version: { type: 'string' }`                      | prints the version of the CLI                       | runs `release` with `version: '1.2.3'`                                        |
| `pin`, `pin` declares `version` with a default                                                   | prints the version of the CLI, and `pin` never runs | runs `pin`                                                                    |
| `ident --version`, `ident` declares the same schema as the global `version`                      | prints the version of the CLI                       | runs `ident` with `version: true`                                             |
| `build -v`, `build` declares `verbose: { type: 'boolean', short: 'v' }`                          | prints the version of the CLI                       | runs `build` with `verbose: true`                                             |
| `build -h localhost`, `build` declares `host: { type: 'string', short: 'h' }`                    | prints the usage                                    | runs `build` with `host: 'localhost'`                                         |
| `-c conf.json`, two global options `config` and `color` use `-c`                                 | `err:arg:invalid-type`                              | `config: 'conf.json'`, and `color` is registered without `-c`, with a warning |
| `deploy --dryRun`, `deploy` declares `dryRun: { type: 'boolean' }`, with `@gunshi/plugin-dryrun` | dry-run mode is on                                  | dry-run mode is off, with a warning                                           |

**How to migrate**

- If a command declares `help` or `version` so that `--help` or `--version` shows the usage or the version, remove the argument, or call `showUsage()` or `showVersion()` of `ctx.extensions['g:global']` from the command
- Use the long name of a global option whose short name a command takes, such as `--version`
- Rename an argument that has the name of the option of `@gunshi/plugin-dryrun`, or give the plugin another name with `dryrun({ name: '...' })`
- In a plugin, check `ctx.env.globalOptions` before you read the value of your global option. Do not take a short name by default: let the user of the plugin choose one
- Update the snapshots of `ctx` or `ctx.env`, which now have `entryCommand` and `globalOptions`

#### Inputs That Now Run the Entry Command

These inputs selected a sub-command in v0.37.3. They now run the entry command, without an error, so they are easy to miss:

| Input                                                                                                     | v0.37.3                               | v1.0                                                |
| --------------------------------------------------------------------------------------------------------- | ------------------------------------- | --------------------------------------------------- |
| `-- deploy`                                                                                               | runs `deploy`                         | runs the entry command, with `deploy` in `ctx.rest` |
| `--config deploy` (a global string option)                                                                | runs `deploy` with `config: 'deploy'` | runs the entry command with `config: 'deploy'`      |
| `--undeclared build`, `-x build` (an option declared nowhere)                                             | runs `build`                          | runs the entry command                              |
| `--force deploy`, when only the loader of the lazy command `deploy` declares `force: { type: 'boolean' }` | runs `deploy` with `force: true`      | runs the entry command, and the loader is not run   |

`--` stops the search for a command, an option that takes a value takes the next argument as its value, and an option declared nowhere is read as taking a value too. The loader of a lazy command is not run to choose the command, so an option that only the loader declares is not known at that point.

**How to migrate**: write options after the command name, and the command name before `--`. For a lazy command, declare the options written before its name in the definition passed to `lazy()`.

#### Lazy Commands

| Lazy command and input                                                                                                               | v0.37.3                                  | v1.0                                                     |
| ------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------- | -------------------------------------------------------- |
| The definition declares `env: { type: 'string', required: true }`, the loader returns `{ run }`, and `deploy` is run without `--env` | runs with no values                      | `Option '--env' is required`                             |
| The definition declares `toKebab: true` and `dryRun`, and `deploy --dry-run` is run                                                  | `--dry-run` is ignored                   | `dryRun: true`                                           |
| The same, with `deploy --dryRun`                                                                                                     | `dryRun: true`                           | `--dryRun` is ignored, as for a command that is not lazy |
| A lazy entry command without a `name`                                                                                                | the loader runs, but the runner does not | the runner runs                                          |

`ctx.name` is now the `name` of the definition, not the key that the command is registered under. A `rendering` of the loader replaces the one of the definition, without merging.

**How to migrate**: use the kebab-case names of the options of a lazy command with `toKebab`, and pass the required arguments that its definition declares.

#### A Plugin That Adds Commands to a CLI Without Sub-Commands

When a plugin adds a command to a CLI that declares no sub-commands, as `@gunshi/plugin-completion` does, `my-cli World` now runs the entry command with `World` as its positional argument. v0.37.3 reported `Command not found: World`. A mistyped command name now goes to the entry command too, as any argument that is not a command name does. An entry command object without `run` still reports it, as a CLI that declares its commands does, since the commands that plugins add are the commands of the CLI. A lazy entry command takes it, as one with `run` does.

**How to migrate**: set `fallbackToEntry: false` to report an argument that is not a command name as an error.

#### Sub-Commands of the Entry Command

The `subCommands` of the entry command were ignored when `cli()` got no `subCommands`. They now give the sub-commands of the CLI:

| CLI and input                                                                                     | v0.37.3                                                 | v1.0                                          |
| ------------------------------------------------------------------------------------------------- | ------------------------------------------------------- | --------------------------------------------- |
| `todo add milk`, when the entry declares `subCommands: { add }` and `cli()` gets no `subCommands` | runs the entry command, or nothing when it has no `run` | runs `add`                                    |
| `todo nope`, the same CLI                                                                         | runs the entry command, or nothing                      | `Command not found: nope`                     |
| `todo 0`, with `subCommands: [add, list]`                                                         | runs `add`                                              | `Command not found: 0`. `todo add` runs `add` |

**How to migrate**: if the entry command declares `subCommands` and also takes positional arguments, remove the `subCommands`, or set `fallbackToEntry: true`.

#### Help Output

The [help output](#help-output-that-describes-each-command) changes for every command (the usage line, the values of options with a default, and the negated forms), and for CLIs with sub-commands, nested sub-commands, commands without `run`, a CLI without a `name`, non-ASCII names, plugins that add commands, arguments whose names start with `no-`, arguments and options without a description, examples with blank lines, and commands that take the name or the short name of a global option. Update the snapshots of `--help` and of `generate()`.

#### Shell Completion

The [completion output](#shell-completion-that-follows-the-cli) gains the global options, and changes with `toKebab`, boolean options, negatable options and `hidden` arguments.

**How to migrate**

- Update the snapshots of the completion output
- Remove a completion handler from a `boolean` argument: it takes no value, and the handler is not called
- A lazy command whose definition has no `args` now runs its loader to complete its arguments. To keep the loader from running, declare the `args` in the definition, with `args: {}` for a command without arguments
- An argument that takes a value under the name of a global option is not completed after a space. Use the `--version=` form

#### `generate()`

`generate()` asks for the usage without adding `-h` to the arguments. For a command that declares an argument named `help`, it now returns the usage instead of running the command and returning an empty string, also with `strict: true`, where v0.37.3 threw `Unknown option: -h`.

#### Argument Error Messages

The messages of the argument errors are reworded. They call an option an option, say what was expected without the names of the types, and name the argument in an error of a parser combinator or of your own `parse`. The built-in `en-US` translations say the same, so a CLI shows the same English with and without the i18n plugin.

| Error                                              | v0.37.3                                                                                               | v1.0                                                                             |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| A missing option                                   | `Optional argument '--env' is required`                                                               | `Option '--env' is required`                                                     |
| A value of the wrong type                          | `Optional argument '--count' should be 'number'`                                                      | `Invalid value for '--count': expected number`                                   |
| A value that is not one of the choices             | `Optional argument '--size' or '-s' should be chosen from 'enum' ["small", "medium", "large"] values` | `Invalid value for '--size' or '-s': expected one of "small", "medium", "large"` |
| A value that `integer({ min: 1, max: 5 })` rejects | `Integer must be <= 5, got 9`                                                                         | `Invalid value for '--replicas': Integer must be <= 5, got 9`                    |
| Arguments that conflict                            | `Optional argument '--json' conflicts with '--yaml'`                                                  | `'--json' conflicts with '--yaml'`                                               |

An option given without its value has [an error code of its own](#args-tokens-1-0) in v1.0, and reads `Option '--env' requires a value`.

**How to migrate**: tell the errors apart by their `code` and `values`, not by their messages, and update the snapshots of the error messages.

#### `--help` and `--version` With an Unknown Option

With `strict: true`, `--help` and `--version` print the help and the version even when an unknown option is given with them, as they do when another argument is wrong: `my-cli deploy --unknown --help` prints the help of `deploy`. v0.37.3 reported the unknown option instead. An unknown command is still reported, with or without `--help`.

**How to migrate**: if a test expects `--help` or `--version` with an unknown option to fail, expect the help or the version instead.

#### Built-in Translations

| Message                                                        | v0.37.3                                     | v1.0                                                                                                  |
| -------------------------------------------------------------- | ------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `--port -5`, `ja-JP`                                           | rejects with a `TypeError`                  | `オプション '--port' or '-p' には値が必要です ('-5' を値として渡すには '--port=-5' と書いてください)` |
| A missing required positional argument with `toKebab`, `en-US` | `Positional argument inputFile is required` | `Positional argument 'input-file' is required`                                                        |
| The negated form of `-f, --force`, `en-US`                     | `Negatable of -f, --force`                  | `Negate -f, --force`                                                                                  |
| The negated form of `-f, --force`, `ja-JP`                     | `否定可能な -f, --force`                    | `-f, --force を打ち消す`                                                                              |

**How to migrate**: if your own translation of `err:arg:missing-value` writes the hint with `{$suggestion}`, remove it, since the hint is now added after the translation. Translate `err:arg:missing-value:hint` for the locales other than `en-US` and `ja-JP`. A translation of `NEGATABLE` without `{$option}` still has the option put after it. To place the option elsewhere, write `{$option}`, as the built-in translations do. A renderer that composes the negated form from `NEGATABLE` passes the option as `{ option }`; without it, the text is `Negate  --x`.

### Migration Checklist

1. Upgrade `gunshi` (or `@gunshi/bone`) and the official plugins to v1.0 together
2. Run your CLI with Node.js or Bun, and install Gunshi and the official plugins from npm rather than JSR
3. Give every `enum` argument its `choices` or a `parse` function, and every `custom` argument a `parse` function. Choose the default of an `enum` argument from its `choices`
4. Handle the new argument error codes and `CommandResolutionError`, and do not branch on the English messages of the errors
5. Add the new keys to your own translations of the built-in resources
6. Write options after the command name, and the command name before `--`. For a lazy command, declare the options written before its name in the definition passed to `lazy()`
7. Check the commands that declare `help`, `version`, the short name of a global option, or the name of the option of `@gunshi/plugin-dryrun`
8. In plugins, do not throw in `setup`, give an `id`, and check `ctx.env.globalOptions` before you read your global options
9. Use the kebab-case names of the options of a lazy command with `toKebab`, and pass the required arguments that its definition declares
10. In scripts, write `--port=-5` rather than `--port -5`, stop giving a value to `--no-*` options, and expect `--verbose=false` to be `false`
11. If a command needs the header before its output, call `showHeader()` of `ctx.extensions['g:global']` in the command
12. If `renderHeader` printed something before a command ran, move it into the command or into `onBeforeCommand`
13. To report argument errors yourself, set `renderValidationErrors: null`. To change the exit code, or to look into the errors, use `onErrorCommand`. If your renderer of the argument errors points to the help itself, pass `helpHint: false`
14. If you set up your AI agent with `npx @gunshi/docs`, set it up with the agent skill of `gunshi` or the manual setup instead
15. Update the snapshots of `--help`, `generate()`, the output of commands, the error messages (now on stderr, [reworded](#argument-error-messages), and followed by [the command that shows the help](#argument-errors-point-to-the-help)), the completion output, `ctx` and `ctx.env`, and the translated error messages
16. If a script gives `--json` to a command that does not support it, remove it, or add `jsonArgs` to the command
17. Type a collection of commands with `SubCommandable` once a command spreads `jsonArgs`
18. In a command decorator, return the result of the runner as it is, and in `onAfterCommand`, expect only a string
19. Remove the `run` that only printed the usage of a command with sub-commands, and give a `run` to one that must do something else when it runs without a sub-command
20. Fix or remove the keys that a command does not have, which are now type errors, and give `resource` with the helpers of `@gunshi/plugin-i18n`
21. Give `run` to every command that has no sub-commands
22. Remove `run` from the definitions of lazy commands
23. Report an error of a lazy loader in `onErrorCommand` or from the rejected `cli()`, not in both
